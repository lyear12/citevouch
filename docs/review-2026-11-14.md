# citevouch 全项目审查：可信引文、作者闭环与维护成本

审查日期：2026-11-14（Asia/Shanghai）。被审基线：`2a98083`，包版本 `0.23.0`。本文是该基线的历史快照，后续修复不应反写为本次已完成。

## 结论与下一阶段方向

项目已经有实质能力：本地来源绑定、逐字引文定位、来源变化检测、离线运行、三种 claim 写法、BibTeX 输入、四种报告，以及经过实际构建与解包验证的发布流程。全量测试、跨平台检查和故意失败的真实 PDF demo 都值得保留。

下一阶段的目标应是：**作者能为最终稿件建立可追溯的引文证据，并在改稿或换源后知道哪些关系需要重新审查。** 成功指标是作者完成一次可信工作流所花的时间、错误放行与误报、候选采用理由及再次使用，而非版本或测试数量。

目前有三件不同的事被一个 `verified` 数量遮在一起：来源字节是否变化、引文是否在来源里、断言是否由引文支持。实现主要回答前两件，附带范围很窄的数字笔误检查；第三件没有通用裁决。还有一个独立且更直接的缺陷：删除词间空白的匹配能把不同引文判为相同。

优先顺序是：修实际错误放行 → 收紧能力契约 → 保证发布源码与验收证据绑定 → 打通分发和最终稿件工作流 → 用真实作者证据决定扩展。暂不新增在线模型裁决、更多格式、视频推广或大规模重构。

执行入口：[短路线图](roadmap.md)、[任务状态](iteration-state.json)、[DeepSeek 每轮推进协议](iteration.md)。本次只交付审查与计划；没有实施下列产品修复，也没有启动定时任务。

## 审查如何进行，以及不能证明什么

- 对 Git 跟踪范围做了全库清点，深读匹配、提取、账本、验证、CLI、报告及关键输入路径，交叉核对英中文档与测试；分别进行产品、核心实现、发布维护三路独立只读评审。没有逐行证明每个解析分支都正确。
- 在临时目录中运行实际 CLI 反例、匹配 API、缓存实验；不改生产源文件，不接触用户原稿。否定反转和大幅数字替换由独立评审复核；后者也用真实 demo PDF 第 6 页的原始多行引文复核。
- 全量本地基线：`PYTHONPATH=src python -m pytest`，**4165 passed，265.69 秒**。`python -m ruff check .` 通过；`sh tools/format_check.sh` 报 **242 files already formatted**。这是改写交接文档之前的基线，不是假阳性不存在的证明。
- 真实 demo：`PYTHONPATH=src python -m citevouch verify demo/manuscript.md --root demo`，**5 claims — 4 verified, 0 moved, 1 missing**，worst `high`，退出 **1**。故意失败的 `fcg-editor` 必须继续失败。
- GitHub 使用只读 API 检查 CI、发布、Issue、PR、分支保护及一次实际发布日志。观察时最近八轮 CI/自动发布均成功，开放 Issue 为零；这不能证明全部分发渠道成功，也不能证明无人使用。
- 全项目 review 工具曾尝试处理 264 个主文件，最终取消：完成 2，待处理 255，7 个因大小/二进制被阻挡，48 次主链失败；累计 93 次调用、约 522.3 秒。**这不是通过报告。** 结论依据来自独立人工式风险审查、可复现实验和测试；未读取私有模型产物来补作“完成证据”。
- 没有证明任意 PDF、BibTeX、TeX 都能正确解析；没有观察独立作者完成整个产品工作流；没有实施真实 PyPI 发布；没有评估仓库之外的历史调度器。性能实验是合成微基准。

## A1 · P0：抹掉词界后认证了另一条引文（实际缺陷）

[matching 的 squashed 分支](../src/citevouch/matching.py#L836) 删除全部空白后搜索，主要检查长度和数字切片；[Match.found](../src/citevouch/matching.py#L234) 将该 tier 当成可认证命中。[verify](../src/citevouch/verify.py#L718) 随后累加 `verified` 并产生 `quote-found`。

父代理复核实际 CLI，`claim` 与 `quote` 都写待查引文，来源只含表中页面文本：

| 页面真实文字 | 待查引文 | tier / 退出码 / 摘要 |
|---|---|---|
| The suspect is nowhere in this room. | The suspect is now here in this room. | squashed / 0 / 1 verified，仅 quote-found |
| The evidence is nowhere in the repository. | The evidence is now here in the repository. | squashed / 0 / 1 verified，仅 quote-found |
| The suspect is now here in this room. | 同左 | exact / 0 / 1 verified |

这不是要求系统理解全文语义，而是“逐字引文对齐”自身的假阳性。新测试需要覆盖负例和正例：词界变化、普通空白折叠、明确的排版断行、连字符、CJK、数字以及跨页。不能靠把所有匹配都变成失败来满足反例；无法证明等价的变换应进入复核候选，不能继续认证。

复现方法：临时目录内写入 `page.txt`、`sources.toml` 与下面的 `m.md`，运行 `citevouch check m.md --root . --format json --no-cache`。再 scan 后运行 verify 与 recorded check，检查兄弟路径。来源文件写 `The suspect is nowhere in this room.`；manifest 写 `[sources]` 及 `paper = "page.txt"`。

````markdown
```claim id=c1 source=paper page=1
quote: |
  The suspect is now here in this room.
claim: |
  The suspect is now here in this room.
```
````

## A2 · P0：能力契约与用户看到的“已验证”不一致（能力边界）

[verify](../src/citevouch/verify.py#L693) 先匹配 `claim.quote`；[数字检查](../src/citevouch/verify.py#L1014) 有意只捕获受约束的近似笔误：至少三位、排除年份、数量形态、近似一键变化，同页已有该数字还可能抑制告警。它不是完整事实一致性检查。

| 引文与断言变化 | 实测结果 |
|---|---|
| 引文 did not improve；断言 improved | exit 0，1 verified，仅 quote-found |
| 引文 40,688；断言 9,800 | exit 0，1 verified，仅 quote-found |
| 引文 40,688；断言 40,689 | exit 1，仍计 1 verified，另有 high claim-number-differs |
| 引文与断言完全一致 | exit 0，1 verified |
| 真实 PDF 第 6 页原引文 40,688 constructions；断言改为 91,234 | exit 0，1 verified，仅 quote-found（独立评审复核） |

`quote-found` 如实说明引文存在，不能因此删除它。问题在于 [README 首句](../README.md#L5) 的 “proves it”、[对比表](../README.md#L51) 的 wrong numbers / drifted paraphrases，以及 [draft 的无需判断](../README.md#L262) 和 [转换器不会假通过](../README.md#L285) 承诺了更多。

先修英中文档、包描述与 [CLI 的 proves it 帮助](../src/citevouch/cli.py#L1060)，实跑顶层及 draft --help 核对主要入口，明确“引文定位通过，支持关系未评估”。保留旧字段及 demo 输出的兼容性；如要新增分维度结果或人工审查状态，先写设计、旧账本行为、迁移和发布级别，不在小修里悄悄改 schema。离线默认继续保留；在线 LLM 可否作为可选辅助，须另有用户需求和质量证据。

## A3 · P0/P1：draft 产物的绿色不等于最终稿件受保护

[confidence](../src/citevouch/draft.py#L982) 和 [原稿名称](../src/citevouch/draft.py#L1021) 只写在 HTML 注释中。[Claim](../src/citevouch/model.py#L487) 没有支持审查状态，也没有原稿内容绑定。

独立评审实测：反向断言仍可获得 medium 共享词提案；随后 check 提案文件退出 0。scan 提案，再改原稿，verify 提案仍退出 0。文档确实要求阅读与回填，因此这不能称为违背“自动保护原稿”的既有实现承诺；但入门展示“立即被 scan/verify 接受”容易掩盖尚未回填。

先把最小闭环演示完整：原稿 → 提案 → 逐项阅证 → 回填最终原稿 → scan 最终原稿 → recorded CI → 改原稿/换源 → 复审与账本 diff。提案文件自身不能成为该演示的最终验收对象。更强的审查状态、原稿绑定和增量复审属于后续设计决策，需用户确认与 schema 迁移。

## A4 · P0：绿色 Test 与发布候选源码没有绑定（静态竞态）

[auto-release](../.github/workflows/auto-release.yml#L45) 检查触发 Test 成功，随后 [checkout](../.github/workflows/auto-release.yml#L54) 浮动 `main`，没有比较 `workflow_run.head_sha`。如果绿色 A 完成时 main 已到 B，可能用 B 计算版本。

[release](../.github/workflows/release.yml#L59) 会切换最终 tag，并 [重跑 Ubuntu/Python 3.12 套件、lint 和 wheel 冒烟](../.github/workflows/release.yml#L94)；所以不能说“发布完全没测”。但这不等于 B 通过了触发阶段八格矩阵和全部外部归档验收。

需要记录绿色源 SHA、生成的发布 commit SHA、版本和产物 digest；main 前进时等待新候选，不借旧绿灯。最终发布树必须对应自己的规定验收证据。这里证明的是代码存在竞态窗口，**没有证明历史某次发布已命中**。

## A5 · P1：PyPI 未分发，阻塞不能只归因于用户没点击

父代理观察 [PyPI JSON](https://pypi.org/pypi/citevouch/json) 返回 404。GitHub Release 已存在，但不是同一分发渠道。

[v0.23.0 实际发布日志](https://github.com/lyear12/citevouch/actions/runs/43395199793/job/131784395859) 记录：

- `2026-11-13T08:43:58.8946813Z Trusted publishing exchange failure`。
- `invalid-publisher: valid token, but no corresponding publisher (Publisher with matching claims was not found)`。
- `2026-11-13T08:43:59.0055498Z` 内部 action 的 `outcome=failure;conclusion=failure`，整轮 run 却是 success；[continue-on-error](../.github/workflows/release.yml#L117) 允许后续 GitHub 发布继续。
- 当次日志警告 reusable workflow 的 Trusted Publishing 路径未受支持、可能损坏。动作实际 SHA 为 `7245906fb61fa33a13554f9d5fb856fe61758086`；公开 identity 的 `workflow_ref` 指向 auto-release，`job_workflow_ref` 指向 release，environment 为 MISSING。

支持警告只描述当时动作版本与执行路径，不说明 PyPI 永远不支持该能力。日志不能区分“从未登记”与“登记身份不匹配”的全部原因。但 [旧维护说明](maintenance.md#L99) 说只登记 release.yml 后下次即发布，证据不足。

拆为三步：工程先确认并实现受支持的发布入口和身份；Owner 按实际身份登记；最后从 PyPI 索引取回指定版本、比对文件 hash、在仓库外新环境安装运行。每步独立记录状态，不能把 GitHub 发布成功合并成 PyPI 成功。

## A6 · P1：发布恢复、tag 身份与同版本资产仍需加固

[自动发布](../.github/workflows/auto-release.yml#L147) 先推 main 再推 tag。后者失败可留下版本已增加、Unreleased 已清空而 tag 缺失；重跑没有完整候选状态可恢复。fallback 检查远端 tag 存在而没有核对 peeled commit。

[release 的多个入口](../.github/workflows/release.yml#L15) 缺统一 publisher 锁，[资产恢复](../.github/workflows/release.yml#L193) 使用 `--clobber`。依赖和构建工具采用下限范围，重建同 tag 不能天然保证字节一致。

应持久化候选，构建一次后重用；所有入口共享发布锁；已有 tag 核对目标 commit，已有资产核对 digest。不一致时停止覆盖，保留已发布事实。发布恢复 stub 测试有价值，但不能替代服务端身份、下载和安装验收。

## A7 · P1：缓存未核对自己记录的源 SHA（容错缺口）

[_load_cache](../src/citevouch/sources.py#L151) 校验 schema、tool、extractor 和 pages 形状，没有核对 [_store_cache 写入的 sha256](../src/citevouch/sources.py#L213)。

临时实验先为真实源 `The intervention did not improve clinical outcomes.` 生成缓存，再把同一缓存文件的 `sha256` 改为 `different-source`，页内容改成肯定句。缓存开启返回肯定句且 match found；`--no-cache` 路径返回真实否定句，同一引文不 found；两次都无提取错误。

这证明错置的合法缓存能影响结果，**没有证明正常运行会自行错置，也不是远程攻击结论**。先校验 SHA、页号连续唯一及提取器身份；异常按缓存 miss 重抽。SHA 自述核对可防错置，不能认证任意本地篡改。可信 CI 的重新提取策略应另行说明。

## A8 · P1：文档的 CI 路径与实际读入内容不同

[手写“等效”命令](../README.md#L347) 缺 `--fail-on medium`，而 [Action](../action.yml#L21) 已正确采用 medium。保留引文、修改来源其他字节后：默认 verify 报 medium source-changed 但退出 0；fresh check 重建基线，不报 source-changed；recorded check 加 medium 才退出 1。

[README 的 SARIF 上传](../README.md#L342) 缺对前步 finding 失败的执行条件，因前步 exit 1 可能跳过上传；需要保留原 gate 失败，同时在报告确实存在时上传，不能用 `continue-on-error` 把论文检查变绿。[不读 bib 的说明](../README.md#L326) 与 [verify 重读记录的书目路径](../src/citevouch/verify.py#L432) 不符；[CLI 内注释](../src/citevouch/cli.py#L343) 也有旧说法。

验收应摘录文档真实命令运行，覆盖源字节变化、页面移动、稿件变化以及失败后的 SARIF 取得；静态搜到 flag 不足以证明流程等价。

## A9 · P1：仓库内实现的是部分自动化，完整自维护仍需执行器

[维护文档](maintenance.md#L10) 描述 Issue → 修复 → 评审 → 合并 → 夜间复盘。[实际 nightly](../.github/workflows/nightly.yml#L13) 是每日 wheel 冒烟，[失败后创建/评论 Issue](../.github/workflows/nightly.yml#L84)。没有仓库内的领取、修复、独立评审、合并验收、复盘消费者。[LESSONS 标记](../LESSONS.md#L3) 仍为 reviewed-through: none。

只读检查时 [main protected=false](https://api.github.com/repos/lyear12/citevouch/branches/main)、[rules=[]](https://api.github.com/repos/lyear12/citevouch/rules/branches/main)，PR 列表为空。文档约束和模板不是服务器端强制。无法由此推断仓库外没有历史 agent 活动。

DeepSeek 每 30 分钟推进是一层外部执行器；这次给出协议和状态台账，**没有实现仓库内 worker、lease 锁或自动合并器**。先保持单写入者和独立评审，再考虑服务器端保护；账号配置列为 needs_owner，不绕过。

## A10 · P2：重复运行与性能应先量化，再优化

[Test](../.github/workflows/test.yml) 共有 11 job；八格矩阵加 lint、acceptance、sdist，按命令统计执行 13 次完整套件：源码 10 次、解包 sdist 3 次；发布另跑一次。[观察到的一轮 Test](https://github.com/lyear12/citevouch/actions/runs/43396279828) 各 job elapsed 合计 **1555 秒，即 25.9 runner 分钟**，墙钟 239 秒。这不是账单分钟，未计系统倍率和免费额度，不能据此报价。

最近 100 条 Release 覆盖 11 月 3—13 日，其中 11 月 9 日 29 条，11 月 10 日 18 条。每 30 分钟推进无需对应一次发版；现有机制只要 Unreleased 非空且 main 通过就会发布，改变发布节奏前须提出明确政策，而不是谎填或隐藏 changelog。

[_best_window](../src/citevouch/matching.py#L978) 每个滑窗重做 SequenceMatcher。独立评审合成实验：固定 1000 个 repeat，needle 末尾 absent，W 为 21/51/101 时单次约 0.051/0.237/0.837 秒；不是普通论文时延。需要真实 PDF、重复文本、长引文三组基准，再决定是否缓存规范化视图、筛候选页或给 fuzzy 预算。超时应报告未知，不能降级为已认证。

CI 优化优先去除同平台同树重复执行，例如一次 sdist suite 同时产出结果和 skip 分类；保留独立平台兼容性、真实负例和外部解包验收。

## A11 · 需求与语料证据需要重新定义

真实 PDF 测试和 39 项书目解析很有价值，但不等于作者已完成最终稿件验收。[draft 的一个集成测试](../tests/test_draft.py#L177) 明确只要求块被识别，允许 exit 0 或 1，不能当成支持关系通过。

[旧 metrics 的无人使用判断](metrics.md#L64) 与 [下载但无 Issue 的推导](metrics.md#L79) 分别推导“无人用”和“工具有效但无人需要”，证据不足；还要区分 nightly 机器人、合成回归、安装下载和外部用户。观察时零 star/fork、低资产下载只是现状，不能证明没有需求。

建议先观察 1 位作者完整完成工作，再在 3 份不同稿件/语料复核。人数是未来验收建议，不是已经得到的用户结论。记录首个可信三元组耗时、候选采用/拒绝原因、未覆盖引用、错误放行、误报与回访。用户文献不得自动上传为公开 fixture；无授权时保留本地数据和可公开的最小复现。

## 三个里程碑与暂停条件
